# ステージ制作 共通仕様

- 対象：LEIR（仮）／3D無双系アクション
- 状態：大枠の制作方針は**確定**。技術詳細・実装方式は**Codex Aで調査・設計**
- 更新：2026-11-05
- 個別ステージ：[草原](Stage_Grassland.md)／遺跡（後日）

## 1. 目的・共通のゲームデザイン【確定】

- 草原、遺跡など、景観の異なる**複数の独立したステージ**を制作する。
- 違いの中心は景観・雰囲気。基本戦闘の構造は共通とし、現段階ではフィールドギミックを要件にしない。
- 多数の敵を集めて斬り払う無双アクションを妨げないこと。移動しやすさ、敵の集団移動と吹き飛ばし、カメラの見通しを重視する。
- 初期は1部屋で基本戦闘を検証する。ステージごとの個別地形・寸法・世界観・装飾・シェーダーの選択は個別仕様に定める。

## 2. アセット構成・再利用【確定／具体的な分割数は仮】

- **Blender完成シーンを形状と配置の正本**とする。ゲーム側で手作業による再配置を必要としないことを目指す。
- 1つの巨大な結合FBXにはせず、**十数〜数十種類程度のFBXアセット**を組み合わせる。数は制作上の仮目安で、固定の上限・下限ではない。
- 分類は次の3つを基本とする。

| 分類 | 役割と分割方針 |
| --- | --- |
| Terrain | ステージ専用の比較的大きな地形メッシュ。戦闘地形、外周、必要な中景・遠景など。原則1〜数個程度を基本に、自然な起伏を優先して無理なタイル化をしない |
| Structure | 大きな構造・地形パーツ。例：岩壁、川岸の要素、遺跡の壁・柱。必要に応じてモジュール化・再利用する |
| Prop | 木・岩・草・花・装飾品など。**同じFBXを複数インスタンスで参照**し、Transformだけを変えて配置する |

- Propは配置数分のFBX複製を出力しない。Structureも必要に応じて再利用する。
- **共有アセット＋ステージ専用アセット**を併用する。複数ステージで使う木・岩などは共通の参照先にまとめ、Terrainや固有の建造物などは各ステージに持たせる。
- ディレクトリ、命名、ステージ間参照の具体規約はCodex Aで決める。

## 3. Blender → FBX・配置JSON【方針確定】

1. Blender上でアセット制作と配置を行い、完成シーンを確認する。
2. 各ユニークアセットをFBXとして出力する。
3. Blenderシーンから、**各インスタンスのアセット参照とTransform（位置・回転・スケール）の組**をJSONへ出力する。
4. ゲームエンジンはFBX群とJSONを読み、Blenderでの配置を再現する。

- 複数の配置が同じメッシュ・FBXを共有できる設計とする。
- JSONは将来的な**インスタンス単位のマテリアル上書き**や、コリジョン参照などの情報を扱えるようにする。
- JSONスキーマ、座標系・単位系、回転形式、ピボット、親子Transform、パス解決、エクスポートの自動化は**未決定**。Codex Aで既存のエンジン仕様を調査する。
- Blenderとエンジンで同じ位置・向き・スケール・参照アセットになることを検証対象とする。

## 4. マテリアル・シェーダー【方針確定】

### 4.1 サブメッシュ／マテリアル

- **1つのFBXに複数マテリアルを許容**する。エンジンはUnityと同様に**サブメッシュ単位でマテリアルを割り当てられる想定**。
- 無理なアトラス化や一律の1マテリアル化をしない。統合が必要かは性能・アセットごとに後から判断する。
- テクスチャは必要に応じてFBXとは別リソースとして管理・共有する。
- 既定マテリアルだけでなく、**配置インスタンス単位のマテリアル上書きにも対応できる情報設計**を目指す（通常は共通割り当てを利用）。

### 4.2 識別情報を優先

- エンジン側の**マテリアルシリアライズ形式は未決定**。Blenderのマテリアルを直接ゲーム用マテリアルとして取り込むことは必須にしない。
- 出力時には少なくとも**マテリアルの識別子、種類（用途・描画分類など）、対応するマテリアルスロット／サブメッシュ**を判別できる情報を残す。
- マテリアルIDの永続化や名称変更への耐性、種類の分類値、テクスチャの参照方法はCodex Aで具体化する。単に表示名だけを恒久IDにするとは確定しない。
- 同じメッシュを参照していても配置ごとに異なるマテリアルを選べる余地を確保する。

### 4.3 シェーダーとBlenderプレビュー

- **最終的なシェーダー・描画表現はゲームエンジン側で実装**する。自由にシェーダーを書ける想定。
- **Blenderでは簡易マテリアル＋テクスチャ表示ができれば十分**。ゲーム側との完全な見た目の一致、BlenderノードのHLSL変換、複雑なシェーダー再現は要求しない。
- Terrainのシェーダーは**ステージ固有**に選択する。マスクブレンドが必要なステージも、通常のテクスチャだけでよいステージもある。全Terrainを単一の共通シェーダー／マスク形式に固定しない。
- 水面・植物・岩などの用途別シェーダーの詳細仕様やリソースの紐付けはCodex A／エンジン実装段階で決める。

## 5. コリジョン【方針確定】

- **描画メッシュとコリジョン用メッシュを分離**し、簡略化した衝突形状をBlender上で作成・配置する。
- **Terrain・複雑なStructure：** 表示メッシュを基に自動簡略化し、必要な部分を手動調整する方針。
- **単純なProp：** Box / Sphere 等のプリミティブ、または簡略化メッシュを使う。草・花などの小さな装飾は原則コリジョンなしを想定。
- **見えない壁：** 必要に応じて専用の簡略化メッシュを手作業で用意する。景観の輪郭に完全一致させる必要はない。
- 描画とは別にコリジョンデータを出力し、ゲーム側で対応付けられるようにする。具体的なファイル形式、物理エンジンへの登録、衝突属性・配置の管理方式はCodex Aで決める。

## 6. Codex Aで調査・詳細設計する事項【未決定】

- 既存エンジンのFBX・サブメッシュ・テクスチャ・マテリアル・コリジョンの対応状況。
- Blenderのシーン構成、FBXの分割／原点ルール、座標変換・ピボット・単位、エクスポータ仕様。
- FBX参照／Transform／マテリアルの識別と上書き／コリジョン対応を記録するJSONスキーマ。
- シェーダー種類の分類とID管理、ゲーム側リソースへの対応付け（マテリアルの実データ形式は未決定）。
- コリジョンの簡略化・編集・出力とランタイム登録、物理判定の範囲。
- Prop再利用時の描画最適化、LOD、テクスチャ予算など。**事前に過度なアトラス化・個数固定をしない**。
- Blender完成シーンに対する出力結果の再現性、参照切れ、アセット重複、必要なON/OFF切替などの検証方法。
- Codex BのGoal実行用の成果物・完了条件・検証手順。

この文書は制作方式の**共通要件**であり、技術実装の詳細仕様・Goalプロンプトではない。個別ステージの地形・演出・マテリアル表現などはそれぞれの仕様書を参照する。
